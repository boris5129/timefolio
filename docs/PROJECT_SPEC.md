# Timefolio — 프로젝트 마스터 프롬프트

## 1. 프로젝트 개요

지금부터 Timefolio라는 개인 시간 자산관리 웹 서비스를 처음부터 개발한다.

단순한 시간 기록, 일정 관리, 할 일 관리 서비스가 아니라 사용자가 자신의 시간을 자산처럼 관리하고, 시간을 확보하거나 절약하며, 확보한 시간을 자신이 원하는 활동에 재투자할 수 있도록 돕는 서비스다.

프로젝트의 전체 개발은 Harness 기반의 단계별 자율 개발 및 검증 방식을 적용한다.

### 서비스명

Timefolio (Time + Portfolio)

추후 서비스명 변경이 가능하도록 구성한다.

### 서비스 슬로건

시간을 아끼는 것을 넘어, 원하는 삶에 투자하다.

### 서비스 핵심 철학

- 시간은 누구에게나 하루 24시간씩 주어지는 자산이다.
- 시간을 단순히 기록하는 것에서 끝나지 않는다.
- 사용자가 시간을 확보하고 원하는 활동에 재투자하도록 돕는다.
- 게임, 취미, 휴식, 수면 역시 가치 있는 활동이다.
- 생산적인 활동만을 강요하지 않는다.
- 하고 싶은 일을 포기하지 않고도 시간을 확보할 수 있는 방법을 제공한다.
- 서비스는 추천과 분석을 제공하되 최종 결정은 사용자가 한다.
- 시간 관리 자체가 사용자에게 부담이 되지 않도록 한다.

### 핵심 서비스 흐름

시간 기록 → 시간 분석 → 시간 확보 및 중첩 → 시간 활용 추천 → 시간 재투자 → 목표 달성 → 시간 결산 → 미래 설계

## 2. 개발 기본 조건

- 개인 개발 프로젝트다.
- 대부분의 개발 작업은 Codex가 담당한다.
- 사용자는 개발을 공부하고 있는 초보 개발자다.
- 사용자는 서비스 방향 결정, 기능 검토, 실제 사용 테스트를 담당한다.
- 사용자가 직접 코드를 작성하거나 복잡한 환경 설정을 해야 하는 상황을 최소화한다.
- 현재는 Windows 환경에서 로컬 실행을 목표로 한다.
- 배포 여부는 서비스 완성 후 결정한다.
- 유료 서비스에 의존하지 않는다.
- 외부 API를 사용하지 않는다.
- OpenAI API, Google Calendar API, 지도 API, 공공데이터 API, 소셜 로그인 등을 초기 버전에 추가하지 않는다.
- 시간 활용 추천은 자체 데이터와 규칙 기반 알고리즘으로 구현한다.
- PC와 스마트폰에서 사용할 수 있는 반응형 웹으로 개발한다.
- 사용자에게 표시되는 모든 메뉴, 설명, 안내 및 오류 메시지는 한국어로 제공한다.
- 불필요하게 복잡한 아키텍처를 사용하지 않는다.
- 향후 기능 확장과 배포가 가능한 구조로 설계한다.
- 별도의 유료 하네스 도구나 에이전트 프레임워크는 사용하지 않는다.

최우선 목표는 실제로 정상 작동하고 안정적으로 사용할 수 있는 완성된 서비스다.

화려한 디자인이나 기능의 개수보다 핵심 기능의 정확성, 안정성, 사용자 편의성을 우선한다.

## 4. Harness 기반 개발 구조

본 프로젝트는 긴 대화 내용이나 Codex의 일시적인 컨텍스트에 의존하지 않는다.

프로젝트 내부에 요구사항, 설계, 진행 상황, 완료 조건, 테스트 결과를 영구적으로 관리한다.

새로운 Codex 세션이나 모델로 변경하더라도 기존 개발을 이어갈 수 있어야 한다.

- AGENTS.md: Codex가 항상 준수해야 하는 핵심 개발 규칙
- PROJECT_SPEC.md: 본 프롬프트의 전체 서비스 요구사항
- ARCHITECTURE.md: 시스템 구조 및 기술 설계
- DATABASE.md: ERD, 테이블 및 데이터 관계
- API_SPEC.md: REST API 명세
- UI_UX.md: 화면 구성 및 디자인 원칙
- BUSINESS_RULES.md: 시간 계산 및 핵심 비즈니스 규칙
- DECISIONS.md: 주요 설계 결정과 변경 이유
- CHANGELOG.md: 기능 변경 이력
- USER_GUIDE.md: 사용자 실행 및 사용 방법
- PLAN.md: 단계별 개발 계획
- PROGRESS.md: 현재 진행 상태와 다음 작업
- ACCEPTANCE.md: 기능별 완료 조건
- IMPLEMENT.md: 개발 및 검증 반복 규칙
- TEST_REPORT.md: 실제 테스트 결과
- ISSUES.md: 발견된 문제, 해결 여부 및 남은 위험 요소

AGENTS.md는 간결하게 유지하고 상세 내용은 관련 문서를 참조하도록 한다.

동일한 정보를 여러 문서에 불필요하게 중복 저장하지 않는다.

최초 프롬프트의 핵심 요구사항을 임의로 생략하거나 축소하지 않는다.

### 4-3. 요구사항 관리

각 핵심 기능에 고유한 요구사항 ID를 부여한다.

예시:

- TF-001: 활동 기록
- TF-002: 반복 일정
- TF-003: 시간 확보
- TF-004: 시간 중첩
- TF-005: 실제 절약 시간 계산
- TF-006: 하고 싶은 일 목록
- TF-007: 시간 재투자
- TF-008: 시간 활용 추천
- TF-009: 미래 시뮬레이션
- TF-010: 통계 및 결산

요구사항 ID와 구현 상태, 완료 조건, 관련 테스트를 연결하여 관리한다.

구현 상태는 다음과 같이 구분한다.

- 미착수
- 구현 중
- 검증 중
- 자동 검증 통과
- 사용자 검증 대기
- 완료
- 보류
- 오류 발생

자동 테스트가 통과했다고 사용자 검증까지 완료된 것으로 표시하지 않는다.

## 5. Harness Loop 실행 규칙

각 개발 단계와 기능 구현 시 다음 과정을 반복한다.

1. 현재 프로젝트 상태 확인
2. 관련 요구사항 및 기존 코드 확인
3. 작업 범위 설정
4. 완료 조건 정의
5. 구현 계획 수립
6. 코드 구현
7. 빌드 및 정적 검사
8. 단위 테스트
9. 통합 테스트
10. 실제 서비스 실행
11. 브라우저 사용자 흐름 검증
12. 실패 원인 분석
13. 오류 수정
14. 재검증
15. 완료 조건 충족 여부 판단
16. 진행 상황 및 테스트 결과 기록
17. 다음 작업 진행

검증이 실패하면 다음 개발 단계로 넘어가지 않는다.

오류가 발생하면 원인을 분석하고 수정한 뒤 다시 검증한다.

테스트를 통과시키기 위해 요구사항을 임의로 변경하거나 테스트를 삭제하거나 검증을 생략하지 않는다.

### 5-1. 자율 작업 범위

다음 작업은 사용자의 추가 지시 없이 가능한 범위에서 직접 수행한다.

- 프로젝트 구조 생성
- 코드 작성 및 수정
- 필요한 무료 라이브러리 설치
- 빌드 오류 수정
- 일반적인 환경 설정 문제 해결
- 테스트 코드 작성
- 테스트 실행
- 데이터베이스 마이그레이션 작성
- 개발용 데이터 생성
- UI 오류 수정
- 문서 업데이트
- 프로젝트 내부 리팩터링
- Git 로컬 변경 이력 관리

사소한 구현 방식이나 합리적인 기본값을 결정하기 위해 사용자에게 반복적으로 질문하지 않는다.

### 5-2. 작업 중단 및 사용자 확인 조건

다음 상황에서는 작업을 중단하고 사용자에게 보고한다.

- 핵심 서비스 방향 변경이 필요한 경우
- 주요 요구사항 변경이 필요한 경우
- 기존 데이터 손실 가능성이 있는 경우
- 유료 서비스 사용이 필요한 경우
- 외부 API 연동이 필요한 경우
- 외부 배포가 필요한 경우
- 관리자 권한이나 사용자 인증이 필요한 경우
- 사용자 컴퓨터의 전역 환경을 크게 변경해야 하는 경우
- 동일한 문제에 대해 세 차례 이상 의미 있는 수정 및 검증을 시도했지만 해결하지 못한 경우
- 필수 개발 환경 문제로 더 이상 진행할 수 없는 경우

무한 반복과 의미 없는 재시도를 방지한다.

### 5-3. 컨텍스트 및 세션 관리

새로운 작업을 시작할 때 다음 내용을 우선 확인한다.

- AGENTS.md
- harness/PROGRESS.md
- harness/PLAN.md
- harness/ACCEPTANCE.md
- 현재 작업과 관련된 요구사항 문서
- 현재 코드 및 Git 상태

매번 전체 문서를 모두 읽을 필요는 없다.

현재 작업에 필요한 문서와 코드만 선택적으로 읽는다.

컨텍스트가 부족해지거나 새로운 세션으로 전환해야 하는 경우 다음 정보를 먼저 기록한다.

- 현재 완료된 기능
- 현재 작업 중인 기능
- 마지막 수정 파일
- 마지막 테스트 결과
- 남아 있는 오류
- 다음에 실행할 작업
- 사용자가 결정한 주요 사항

새로운 세션에서 기존 프로젝트를 처음부터 다시 구현하지 않는다.

## 6. 핵심 기능 상세 명세

### 6-1. 시간 가계부 (Time Budget)

사용자가 하루 동안 어떤 활동에 시간을 사용했는지 기록하고 분석할 수 있도록 한다.

지원 기능:

- 활동 등록, 조회, 수정, 삭제
- 시작 시간 및 종료 시간 설정
- 소요 시간 자동 계산
- 활동 카테고리 선택
- 메모 작성
- 날짜별 활동 조회
- 하루 타임라인
- 자주 사용하는 활동 빠른 등록
- 전날 일정 복사
- 계획된 활동과 실제 활동 구분

기본 카테고리:

- 수면
- 업무
- 학업
- 이동
- 식사
- 운동
- 취미
- 게임
- 영상 시청
- 자기계발
- 인간관계
- 휴식
- 기타

사용자는 카테고리를 추가, 수정, 삭제할 수 있다.

카테고리별 색상과 아이콘을 지정할 수 있도록 한다.

하루 24시간 중 다음 정보를 구분하여 표시한다.

- 실제 기록 시간
- 예정된 활동 시간
- 기록되지 않은 시간
- 남은 계획 가능 시간
- 주 활동 시간
- 보조 활동 시간

기록되지 않은 시간을 자동으로 낭비한 시간이나 자유시간으로 판단하지 않는다.

### 6-2. 반복 일정

반복되는 생활 패턴을 매번 입력하지 않도록 한다.

예시:

- 평일 07:30~08:30 지하철 이동
- 평일 09:00~17:50 학원 수업
- 평일 18:00~19:00 귀가
- 매일 23:30~07:00 수면
- 월·수·금 20:00~21:00 운동

지원 기능:

- 매일 반복
- 평일 반복
- 주말 반복
- 특정 요일 반복
- 반복 시작일 및 종료일
- 특정 날짜만 수정
- 반복 일정 전체 수정
- 특정 날짜 제외
- 예정된 활동을 실제 기록으로 전환

반복 일정은 예정된 활동으로 처리한다.

사용자의 확인 없이 실제 활동을 수행한 것으로 기록하지 않는다.

같은 반복 일정이 중복 생성되지 않도록 한다.

### 6-3. 시간 확보 (Time Saving)

사용자가 기존 활동 시간을 줄여 다른 활동에 사용할 시간을 확보하는 기능이다.

예시:

- 게임 120분 → 90분: 30분 확보
- 유튜브 90분 → 60분: 30분 확보
- SNS 60분 → 30분: 30분 확보

사용자 입력 정보:

- 줄이고 싶은 활동
- 기존 평균 활동 시간 또는 기준 계획 시간
- 변경하고 싶은 활동 시간
- 실천 요일 및 빈도
- 시작 날짜
- 적용 기간

자동 계산 정보:

- 하루 예상 확보 시간
- 일주일 예상 확보 시간
- 한 달 예상 확보 시간
- 1년 예상 확보 시간
- 계획 대비 실제 확보 시간
- 확보 목표 달성률

실제 확보 시간은 비교 기준과 실제 활동 기록을 바탕으로 계산한다.

단순히 계획을 등록했다고 실제 시간을 확보한 것으로 처리하지 않는다.

기록이 누락된 활동을 무조건 줄인 활동으로 판단하지 않는다.

사용자가 실제로 활동을 줄였는지 확인할 수 있도록 한다.

계획된 확보 시간과 실제 확보 시간을 반드시 구분한다.

### 6-4. 시간 중첩 (Time Stacking)

Timefolio의 가장 중요한 차별화 기능 중 하나다.

특정 활동을 수행하는 동안 다른 활동을 함께 수행하여 기존에 별도로 사용할 예정이었던 시간을 절약하는 기능이다.

활동을 포기하거나 줄이지 않고도 시간을 확보할 수 있도록 한다.

#### 예시 1: 지하철 이동과 취미생활

기존 생활 패턴:

- 지하철 이동 60분
- 저녁 유튜브 시청 60분
- 총 필요 시간 120분

변경된 생활 패턴:

- 지하철 이동 중 유튜브 시청 60분
- 별도 유튜브 시청 시간 0분
- 실제 필요 시간 60분
- 절약한 시간 60분

#### 예시 2: 운동과 영상 시청

기존 생활 패턴:

- 스태퍼 운동 30분
- 애니메이션 시청 30분

변경된 생활 패턴:

- 스태퍼 운동 중 애니메이션 시청
- 실제 필요 시간 30분
- 절약한 시간 30분

#### 예시 3: 부분 중첩

- 지하철 이동 60분
- 이동 중 공부 40분
- 실제 경과 시간 60분
- 이동 활동 시간 60분
- 공부 활동 시간 40분
- 활동별 수행 시간 합계 100분
- 실제 시간 소비 60분
- 중첩 시간 40분

#### 지원 기능

- 주 활동 선택
- 보조 활동 선택
- 중첩 시작 및 종료 시간 설정
- 실제 중첩 시간 자동 계산
- 중첩 활동 메모
- 반복 중첩 일정
- 중첩 가능한 활동 추천
- 예상 절약 시간
- 실제 절약 시간
- 대체한 기존 활동 연결
- 부분 대체 처리

#### 중요 계산 규칙

주 활동과 보조 활동 시간을 단순 합산하여 하루 사용 시간이 24시간을 초과하는 문제가 발생하면 안 된다.

실제 경과 시간과 활동별 수행 시간을 구분한다.

실제 시간 소비는 활동 시간 구간의 합집합을 기준으로 계산한다.

중첩 시간은 실제로 겹치는 시간 구간을 기준으로 계산한다.

중첩 활동을 했다고 무조건 시간을 절약한 것으로 처리하지 않는다.

원래 저녁에 40분 공부할 예정이었고 이동 중 공부가 해당 활동을 완전히 대체했다면 40분을 절약한 것으로 처리한다.

원래 별도 공부 계획이 없었다면 추가 활동으로 기록하고 실제 절약 시간에는 포함하지 않는다.

40분 중 20분만 기존 활동을 대체했다면 실제 절약 시간은 20분이다.

실제 절약 시간은 중첩 시간과 기존 대체 가능 시간을 초과할 수 없다.

사용자가 절약 시간 인정 여부와 실제 대체 시간을 확인하거나 수정할 수 있도록 한다.

동일한 기존 활동 시간을 시간 확보와 시간 중첩에서 중복 계산하지 않는다.

하나의 활동에서 여러 보조 활동이 중첩되더라도 동일한 실제 시간 절약분을 중복 계산하지 않는다.

초기 버전은 주 활동 하나와 보조 활동 하나를 중심으로 안정적으로 구현한다. 여러 보조 활동 지원은 추후 확장할 수 있도록 설계한다.

#### 기본 중첩 추천 데이터

- 지하철 이동 + 독서
- 지하철 이동 + 인터넷 강의
- 지하철 이동 + 유튜브 시청
- 버스 이동 + 영어 단어 암기
- 실내 운동 + 영상 시청
- 산책 + 오디오북
- 집안일 + 팟캐스트
- 대기 시간 + 일정 정리

사용자는 중첩 조합을 직접 추가하거나 추천에서 제외할 수 있다.

운전 중 영상 시청 등 안전에 영향을 주는 조합은 추천하지 않는다.

집중력이 필요한 활동이나 충분한 휴식에 무리한 중첩을 강요하지 않는다.

### 6-5. 하고 싶은 일 목록 (Wish List)

사용자가 평소 하고 싶었지만 시간이 부족하여 하지 못했던 활동을 등록하는 기능이다.

예시:

- 정보처리기사 공부
- 개인 프로젝트 개발
- 책 읽기
- 운동하기
- 게임 플레이
- 영화 감상
- 여행 준비
- 충분한 휴식

등록 정보:

- 활동명
- 카테고리
- 설명
- 목표 시간
- 현재 누적 시간
- 목표 완료 날짜
- 우선순위
- 한 번에 필요한 최소 시간
- 진행 상태

진행 상태:

- 시작 전
- 진행 중
- 완료
- 보류

목표 시간과 완료 날짜는 필수가 아니다.

단순한 취미 활동도 자유롭게 등록할 수 있도록 한다.

목표 시간을 달성했다고 실제 자격증 취득이나 프로젝트 완료를 자동으로 판단하지 않는다.

시간 목표 달성과 실제 목표 완료를 구분한다.

### 6-6. 시간 재투자 (Time Investment)

시간 확보 및 시간 중첩으로 얻은 시간을 다른 활동에 배분하는 기능이다.

예시:

오늘 확보한 시간 90분:

- 자격증 공부 40분
- 개인 프로젝트 30분
- 휴식 20분

지원 기능:

- 예상 확보 시간 확인
- 실제 확보 시간 확인
- 하고 싶은 일 목록에서 활동 선택
- 새로운 활동 직접 입력
- 여러 활동에 시간 분할
- 추천 배분 적용
- 추천 배분 수정
- 실제 사용 시간 기록
- 목표 진행률 자동 반영
- 미사용 확보 시간 확인

계획된 재투자 시간과 실제 재투자 시간을 구분한다.

실제 확보한 시간보다 많은 시간을 확보 시간으로 재투자하지 못하도록 한다.

예상 확보 시간은 미래 계획에 사용할 수 있지만 실제 확보 시간과 별도로 표시한다.

확보 시간과 재투자 기록의 연결 관계를 관리한다.

동일한 실제 활동을 여러 목표에 연결하더라도 실제 시간 소비와 재투자 시간을 중복 합산하지 않는다.

시간은 실제로 다음 날까지 저장할 수 있는 자산이 아니다.

사용하지 않은 자유시간이 다음 날의 실제 사용 가능 시간으로 누적되지 않도록 한다.

과거 확보 시간은 통계 기록으로만 누적한다.

### 6-7. 시간 활용 추천 시스템

외부 생성형 AI API를 사용하지 않고 규칙 기반 추천 시스템으로 구현한다.

추천에 활용할 정보:

- 사용자가 확보한 시간
- 하고 싶은 일 목록
- 목표 우선순위
- 목표 완료일까지 남은 기간
- 목표 달성률
- 활동별 최소 필요 시간
- 사용자 선호 활동
- 최근 시간 사용 패턴
- 사용자가 선택한 추천 유형

추천 유형:

1. 목표 달성 중심
2. 균형 잡힌 생활
3. 취미 및 휴식 중심
4. 사용자 맞춤 우선순위

예를 들어 확보한 시간이 60분인 경우 다음과 같이 추천할 수 있다.

목표 달성 중심:

- 자격증 공부 40분
- 개인 프로젝트 20분

균형 중심:

- 공부 30분
- 운동 15분
- 휴식 15분

취미 중심:

- 게임 30분
- 독서 20분
- 휴식 10분

추천 결과에는 추천 이유를 표시한다.

예시:

정보처리기사 시험까지 남은 기간이 짧고 현재 목표 달성률이 낮아 공부 시간을 우선적으로 추천했습니다.

추천 알고리즘은 설명 가능한 방식으로 설계한다.

우선순위, 목표 긴급도, 남은 목표 시간, 최소 활동 시간 등을 활용하여 추천 점수를 계산한다.

추천 가능한 시간이 부족하면 무리하게 활동을 분할하지 않는다.

등록된 목표가 없거나 데이터가 부족한 경우 기본 추천과 직접 입력 기능을 제공한다.

추천 결과는 사용자가 자유롭게 변경하거나 거절할 수 있다.

실제로 생성형 AI를 사용하지 않으므로 AI가 분석했다고 허위 표시하지 않는다.

### 6-8. 미래 시간 시뮬레이션

현재 생활 패턴을 변경했을 때 미래에 얼마나 많은 시간을 확보하거나 다른 활동에 사용할 수 있는지 계산한다.

사용자 입력:

- 줄일 활동
- 하루 줄일 시간
- 중첩할 활동
- 예상 중첩 시간
- 예상 대체 시간
- 실천 빈도
- 시뮬레이션 기간
- 확보한 시간의 사용 목적
- 활동별 배분 비율
- 예상 실천율

지원 기간:

- 하루
- 일주일
- 한 달
- 3개월
- 6개월
- 1년
- 5년
- 10년
- 사용자 지정 기간

결과 표시:

- 예상 확보 시간
- 예상 중첩 절약 시간
- 총 예상 확보 시간
- 활동별 예상 재투자 시간
- 24시간 기준 일수
- 8시간 활동 기준 일수
- 목표 시간 달성 예상 시점

실천율을 0~100% 범위에서 설정할 수 있도록 한다.

기간 계산은 실제 달력 날짜와 선택한 반복 요일을 기준으로 처리한다.

윤년, 월별 일수 차이 등을 고려한다.

시간 확보와 중첩으로 절약되는 시간이 동일한 활동에서 중복 발생하지 않도록 한다.

예상 결과는 실제 달성 결과가 아니라 가정에 따른 시뮬레이션임을 명확하게 표시한다.

### 6-9. 통계 및 결산

지원 기간:

- 일간
- 주간
- 월간
- 연간
- 사용자 지정 기간

주요 통계:

- 활동별 사용 시간
- 카테고리별 사용 시간
- 실제 경과 시간
- 활동별 수행 시간
- 계획 시간과 실제 시간 비교
- 활동 감소로 확보한 시간
- 활동 중첩으로 절약한 시간
- 총 확보 시간
- 실제 재투자 시간
- 사용하지 않은 확보 시간
- 목표 진행률
- 이전 기간 대비 변화
- 반복 일정 실천율

실제 데이터베이스 데이터를 기반으로 그래프를 표시한다.

통계 계산에서 중첩 활동을 중복 합산하지 않는다.

실제 시간 기준 그래프와 활동 수행 시간 기준 그래프를 명확히 구분한다.

데이터가 없는 경우 가짜 데이터를 표시하지 않고 적절한 빈 화면을 제공한다.

## 8. UI/UX 디자인 요구사항

금융 자산관리 서비스와 현대적인 시간 관리 서비스가 결합된 느낌으로 구성한다.

토스와 같은 서비스의 직관적인 정보 전달 방식을 참고하되 특정 서비스의 디자인을 그대로 복제하지 않는다.

### 디자인 방향

- 깔끔하고 현대적인 디자인
- 불필요한 장식 최소화
- 충분한 여백
- 직관적인 숫자 및 그래프
- 가독성 높은 한국어 폰트
- 일관된 색상 체계
- 라이트 모드 및 다크 모드
- 부드럽고 과하지 않은 애니메이션
- 모바일 터치 환경 고려
- 접근성 및 명확한 대비 고려

### 색상 체계

- 기본 색상: 네이비 또는 차분한 블루
- 시간 확보: 그린
- 시간 중첩: 퍼플
- 시간 재투자: 블루 또는 틸
- 일반 활동: 카테고리별 색상
- 오류 및 경고: 레드 또는 오렌지

색상만으로 상태를 구분하지 않고 텍스트와 아이콘을 함께 사용한다.

### PC 화면

- 좌측 사이드바
- 상단 날짜 및 사용자 정보
- 중앙 대시보드
- 카드 형태의 주요 통계
- 그래프 및 타임라인
- 빠른 활동 등록

### 모바일 화면

- 화면 크기에 맞는 반응형 레이아웃
- 하단 내비게이션 또는 적절한 모바일 메뉴
- 큰 터치 영역
- 빠른 활동 등록
- 한 손으로 조작하기 편한 구조
- 불필요한 가로 스크롤 금지

모바일 앱을 별도로 개발하지 않는다.

추후 PWA로 확장할 수 있는 구조를 고려하되 초기 필수 기능으로 구현하지 않는다.

### 사용자 편의성

활동 등록, 시간 중첩 등록, 시간 재투자 등록은 최대한 적은 조작으로 완료할 수 있도록 한다.

시간 입력을 편리하게 하기 위해 자주 사용하는 활동, 최근 활동, 반복 일정 등을 활용한다.

삭제, 복원 등 중요한 작업에는 확인 절차를 제공한다.

로딩, 성공, 실패, 빈 데이터 상태를 명확하게 표시한다.

## 9. 데이터베이스 설계

다음 테이블을 참고하되 실제 요구사항과 정규화에 따라 통합하거나 분리할 수 있다.

- users: 사용자 정보

- planned_activities: 예정 활동
- time_saving_plans: 시간 확보 계획
- time_saving_records: 실제 시간 확보 기록
- time_stacking_records: 시간 중첩 기록
- time_stacking_rules: 중첩 추천 규칙
- wishlist_items: 하고 싶은 일
- goals: 목표 정보
- time_investments: 시간 재투자 기록
- simulation_scenarios: 미래 시뮬레이션 설정
- user_settings: 사용자 설정

초기 버전에서 사용하지 않는 테이블을 무조건 모두 생성하지 않는다.

단계별 기능 구현에 맞춰 Flyway 마이그레이션을 추가한다.

### 필수 설계 원칙

- 기본키 및 외래키 명확히 정의
- 데이터 정규화 고려
- 중복 데이터 최소화
- 필요한 인덱스 설정
- 사용자별 데이터 분리
- 생성 및 수정 시간 관리
- 예정 시간과 실제 시간 구분
- 주 활동과 보조 활동 구분
- 확보 시간과 재투자 시간의 연결 관계 관리
- 중복 확보 및 중복 재투자 방지
- 정수 단위 시간 계산
- 날짜를 넘어가는 활동 처리
- 시간대 처리
- 트랜잭션 및 데이터 무결성 보장

시간 데이터는 정수 초 또는 분 단위를 일관되게 사용한다.

화면에서 시간과 분으로 변환하여 표시한다.

실제 활동 기록은 시작 시각과 종료 시각을 함께 관리한다.

기본 사용자 시간대는 Asia/Seoul로 설정한다.

날짜를 넘어가는 활동은 실제 날짜별 시간 구간으로 분리하여 통계를 계산한다.

시간 기록이 수정되거나 삭제되었을 때 관련 확보 기록, 재투자 기록, 목표 진행률에 불일치가 발생하지 않도록 처리한다.

중요한 시간 계산 로직은 프론트엔드와 백엔드에서 서로 다른 방식으로 중복 구현하지 않는다.

최종 검증 및 계산 기준은 백엔드에 둔다.

## 11. 인증 및 보안

초기에는 개인용 로컬 서비스이지만 추후 다중 사용자 서비스로 확장할 수 있도록 설계한다.

- 일반 아이디 또는 이메일 기반 회원가입 및 로그인
- 안전한 비밀번호 해싱
- 인증된 사용자만 자신의 데이터에 접근
- 사용자별 데이터 접근 권한 검증
- SQL Injection 방지
- XSS 방지
- CSRF 및 CORS 적절한 처리
- 환경변수를 통한 민감한 설정 관리
- 비밀번호 및 DB 접속 정보를 Git에 저장하지 않음
- 민감한 개인정보를 로그에 출력하지 않음

외부 소셜 로그인은 구현하지 않는다.

인증 방식은 로컬 웹 서비스에 적합한 단순하고 안전한 방식을 선택한다.

불필요하게 복잡한 인증 시스템을 도입하지 않는다.

개발용 계정과 테스트 데이터는 개발 환경에서만 사용할 수 있도록 한다.

로컬 서버는 기본적으로 localhost에 바인딩한다.

스마트폰에서 동일 네트워크를 통한 테스트가 필요한 경우 별도의 개발 설정과 실행 방법을 제공한다.

사용자 승인 없이 외부 네트워크에 서비스를 공개하지 않는다.

## 14. 자동 검증 시스템

프로젝트 환경에 맞는 자동화 검증 스크립트를 구성한다.

검증 대상:

- 프론트엔드 빌드
- TypeScript 타입 검사
- ESLint 검사
- 프론트엔드 단위 테스트
- 백엔드 빌드
- 백엔드 단위 테스트
- 데이터베이스 연결
- 데이터베이스 마이그레이션
- REST API 통합 테스트
- 핵심 사용자 흐름 E2E 테스트
- PC 화면 검증
- 모바일 화면 검증
- 브라우저 콘솔 오류 확인

가능하면 Playwright를 활용하여 실제 브라우저에서 핵심 사용자 흐름을 검증한다.

검증에 필요한 테스트 데이터는 실제 사용자 데이터와 분리한다.

자동 테스트가 실제 사용자 데이터를 삭제하거나 변경하지 않도록 한다.

Windows에서 실행할 수 있는 통합 검증 스크립트를 제공한다.

예시:

```powershell
.\scripts\verify.ps1
```

검증 스크립트는 실패 시 적절한 종료 코드를 반환하고 어떤 검증이 실패했는지 표시해야 한다.

구현되지 않은 기능에 대한 검증을 통과했다고 표시하지 않는다.

실행 환경 제약으로 검증할 수 없는 항목은 미검증 상태로 기록한다.

## 16. 실행 환경 및 사용자 편의성

사용자가 개발 환경에 익숙하지 않다는 점을 고려한다.

복잡한 명령어를 매번 직접 입력하지 않아도 되도록 실행 스크립트를 제공한다.

예시:

```powershell
.\scripts\setup.ps1
.\scripts\start.ps1
.\scripts\stop.ps1
.\scripts\verify.ps1
```

setup.ps1:

- 필수 환경 확인
- 프로젝트 의존성 설치
- 필요한 설정 파일 안내
- 데이터베이스 연결 확인

start.ps1:

- 프론트엔드 및 백엔드 실행
- 필요한 서비스 상태 확인
- 실행 주소 표시
- 가능하면 브라우저 접속 안내

stop.ps1:

- 해당 프로젝트에서 실행한 프로세스만 안전하게 종료
- 다른 프로그램이나 사용자의 기존 서비스에 영향 방지

verify.ps1:

- 현재 구현된 기능의 자동 검증 수행
- 실패 항목 표시
- 테스트 결과 기록

사용자의 DB 비밀번호 등 직접 입력이 필요한 정보는 명확하게 안내한다.

환경 설정이나 프로그램 설치가 필요하다면 사용자가 따라 할 수 있도록 한국어로 구체적으로 설명한다.

## 17. Codex 공통 작업 규칙

- 가능한 작업은 직접 파일을 생성하고 구현한다.
- 코드만 채팅에 출력하고 작업을 끝내지 않는다.
- 기존 파일이 있다면 내용을 먼저 확인한다.
- 사용자의 기존 파일을 임의로 삭제하거나 덮어쓰지 않는다.
- 프로젝트 폴더 외부 파일을 임의로 변경하지 않는다.
- 사용자의 기존 작업을 되돌리지 않는다.
- 유료 API, 유료 서비스, 외부 배포는 사용자 승인 없이 진행하지 않는다.
- 데이터베이스 삭제 등 데이터 손실 가능성이 있는 작업은 사용자에게 먼저 확인한다.
- 환경 설정 문제를 발견하면 가능한 범위에서 직접 해결한다.
- 불필요하게 사소한 질문을 반복하지 않는다.
- 합리적인 기본값으로 진행할 수 있는 작업은 직접 판단한다.
- 서비스 방향이나 핵심 기능 변경은 사용자에게 먼저 확인한다.
- 구현 후 실제 빌드 및 테스트를 수행한다.
- 오류가 발생하면 원인을 분석하고 수정한다.
- 임시 구현이나 우회 처리가 필요한 경우 문서에 기록한다.
- 구현하지 않은 기능을 완료된 것처럼 표시하지 않는다.
- 프론트엔드 버튼은 실제 기능과 연결되어 있어야 한다.
- 가짜 데이터로 실제 기능을 구현한 것처럼 표시하지 않는다.
- 주요 변경 사항은 한국어로 설명한다.
- 지나치게 복잡한 코드를 피한다.
- 필요한 부분에만 주석을 작성한다.
- 단계별 Git 변경 이력을 관리한다.
- GitHub 원격 저장소 생성이나 코드 업로드는 사용자 승인 없이 진행하지 않는다.
- 현재 모델의 능력이나 추론 수준으로 해결하기 어려운 문제가 발생하면 사용자에게 명확하게 안내한다.

### 모델 변경 안내

더 높은 성능의 Codex 모델 또는 추론 수준이 필요하다고 판단되는 경우 다음과 같이 눈에 띄는 큰 제목으로 보고한다.

# CODEX 모델 또는 추론 수준 변경 권장

변경을 권장하는 이유, 현재 해결되지 않은 문제, 필요한 작업을 설명한다.

불필요한 모델 변경을 반복적으로 권장하지 않는다.
